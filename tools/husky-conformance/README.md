# husky conformance suite

Upstream husky's own test suite, vendored **unmodified**, plus a small driver
that runs it against the husky this repository installed.

```
run.sh                 our driver (POSIX sh); the only file here we wrote
upstream/test.sh       copied verbatim from tag v9.1.7
upstream/test/*.sh     the 12 spec tests + functions.sh, copied verbatim
upstream/LICENSE       husky's MIT licence, copied verbatim
```

## Why

Every test in `tests/` starts *after* husky: it calls a hook module, or a shim,
in a repository where the wiring is already assumed correct. If
`core.hooksPath` is wrong, `.husky/_/` was generated by another husky version,
a generated shim is not executable, or `HUSKY=0` is not honoured, the whole
hook layer silently stops running — and none of our tests would notice.

Upstream's suite is the specification for that chain, so this runs it as-is
rather than restating it. A pass means "the husky we depend on still behaves the
way this integration assumes, on this OS and this Node".

## How the driver differs from upstream's `test.sh`

`upstream/test.sh` packs **this** repository (`npm pack`) and runs
`sh test/<name>.sh` for all twelve. That works in the husky repository and
nowhere else. `run.sh` does the equivalent here:

1. `npm pack node_modules/husky` — the installed module, the bytes a consumer
   would get from the registry — and move it to `/tmp/husky.tgz`. The tarball
   path is hard-coded because `test/functions.sh` hard-codes it
   (`setup()` creates `/tmp/husky-test-<name>`, `install()` runs
   `npm install ../husky.tgz`). Under Git Bash `/tmp` is the Windows temp
   directory, so native `npm` in the tests resolves it there too.
2. Run `sh upstream/test/<name>.sh` from `upstream/`, one per test.
3. Print a `TEST / RESULT / WHAT IT PINS DOWN` table and a tail of each
   failing test's log, which is left in `/tmp/husky-conformance-logs`.

Flags:

```sh
sh tools/husky-conformance/run.sh            # skip quietly if node/npm/git is absent
sh tools/husky-conformance/run.sh --require  # fail instead of skip (CI)
sh tools/husky-conformance/run.sh --only 9   # one test, for debugging
```

`allow_reason()` lists tests knowingly allowed to fail on some platform. It is
**empty on purpose**: all twelve pass on Git Bash / node 24, and CI runs the
same twelve on ubuntu, macOS and Windows. The report shouts if a listed test
starts passing, so the list cannot rot into a bin of real failures.

## In CI

`.github/workflows/hooks.yml`, job `hooks`, runs `run.sh --require` with
`shell: bash` on ubuntu, macOS and Windows (one Python version — the suite is
about Node and git, not Python). Upstream's own CI runs the same suite on
ubuntu/macOS/Windows across Node 18, 20 and 22; ours pins whatever Node the job
installed, because that is the version this repository actually uses.

It is deliberately **not** part of `pytest`: it needs node and npm, and it
takes about a minute because each test does a real `npm install` in a throwaway
repository. The pre-push gate runs the Python suite on every push, and that
should stay fast.
