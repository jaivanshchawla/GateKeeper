# Git hooks with husky

This repo runs its git hooks through [husky](https://github.com/typicode/husky) 9.
Husky is only the *installer*: it owns `core.hooksPath` and keeps two-line
shims in `.husky/`. Every rule lives in `scripts/hooks/`, in Python, next to
the rest of the project.

For how each husky feature is used here — and which ones deliberately are not —
see [HUSKY-UPSTREAM.md](HUSKY-UPSTREAM.md).

## Why husky at all

Before this, hook installation was split across two mechanisms that could not
both work:

| Mechanism | What it wrote | Problem |
|-----------|---------------|---------|
| `.pre-commit-config.yaml` + `pre-commit install --hook-type pre-push` | `.git/hooks/pre-push` | Untracked, so a fresh clone had no hook until someone ran the install command |
| `gatekeeper init` (the CLI) | `.git/hooks/pre-push` | Overwrote the file above, and baked in an absolute Windows path |

Git executes exactly one file per hook, so these silently clobbered each other,
and nothing tracked in the repo guaranteed a hook was installed at all.

Husky replaces that with one tracked, declarative installer: `npm install`
runs `prepare` → `core.hooksPath` is set and the shims are live.

## Layout

```
package.json            husky devDependency + the npm scripts below
.gatekeeper.yml         protected_branches, rule severities
.husky/
  <hook>                all 14 two-line shims (see the table below)
  applypatch-msg  pre-applypatch  post-applypatch  pre-commit
  pre-merge-commit  prepare-commit-msg  commit-msg  post-commit
  pre-rebase  post-checkout  post-rewrite  post-merge  pre-push
  pre-auto-gc
  install.mjs           CI/production-safe installer (the `prepare` script)
  uninstall.mjs         reverses the install (husky v9 removed this command)
  lib/bootstrap.sh      finds a working Python 3 and runs the hook module
  lib/common.sh         shell helpers; opt-in tty guard for Windows
  _/                    generated by husky (gitignored)
scripts/hooks/
  _runtime.py           repo root, interpreter, git helpers, hook inventory,
                        tracing, the gate-run marker
  _policy.py            protected branches + .gatekeeper.yml
  _checks.py            staged-content checks shared by the two guard hooks
  _events.py            the one local event log (outcome tracking)
  commit_msg.py         conventional-commit rules (shared with applypatch-msg)
  pre_commit.py  pre_applypatch.py  pre_push.py  verify.py
  applypatch_msg.py  prepare_commit_msg.py
  pre_merge_commit.py  pre_rebase.py
  post_commit.py  post_applypatch.py  post_merge.py
  post_checkout.py  post_rewrite.py  pre_auto_gc.py
tests/test_hooks.py             unit tests
tests/test_hook_integration.py  every hook against a real temporary git repo
```

Three rules keep this readable:

1. **`.husky/<hook>` files contain no logic.** Two lines — source the
   bootstrap, delegate to a module. Anything longer belongs in `scripts/hooks/`
   where it can be unit-tested.
2. **Interpreter resolution happens in one place per question.**
   `bootstrap.sh` decides which Python can *start* a hook; `_runtime.py` decides
   which Python runs the project's tooling.
3. **The hook list has one owner.** `_runtime.HOOKS` is read by the doctor, the
   tests and these docs, so a rename cannot silently disable a hook.

Hooks are invoked as `python -m scripts.hooks.<hook>`, not by file path. Running
a file puts `scripts/` on `sys.path[0]`, which is what once forced every hook
script to carry its own four-line `sys.path` shim.

## The hooks

`blocks` can abort the git command; `reports` is advisory.

| Hook | Kind | What it does |
|------|------|--------------|
| `pre-commit` | blocks | `ruff` on the **staged Python files only**; leftover merge-conflict markers (via git's own `diff --cached --check`) |
| `commit-msg` | blocks | conventional subject: `type(scope): subject`, types read off this repo's history |
| `applypatch-msg` | blocks | the same subject rules for `git am`, which never runs `commit-msg` |
| `pre-applypatch` | blocks | the same staged-content checks as `pre-commit`, for `git am`, which never runs it |
| `post-applypatch` | reports | records the commit `git am` created, in the shared event log |
| `prepare-commit-msg` | reports | warns on a direct commit to a protected branch (`direct_to_main`); seeds the type list as comments when an editor opens |
| `pre-merge-commit` | blocks | refuses to merge into a protected branch |
| `pre-rebase` | blocks | refuses to rebase a protected branch |
| `pre-push` | blocks | Gate 1 scoring (advisory), diff-scoped `ruff`, then `pytest` |
| `post-commit` | reports | records the commit for local outcome tracking |
| `post-merge` | reports | records the merge; flags merges that changed the gate itself |
| `post-checkout` | reports | branch gate context |
| `post-rewrite` | reports | records amended/rebased-away shas, so earlier scores are known to be stale |
| `pre-auto-gc` | declines | skips git's background `gc --auto` while a gate hook is running |

All 14 are implemented — every shim husky writes a dispatcher for has a real
script behind it, and the doctor asserts that (`HOOKS` and `HUSKY_HOOKS` must be
the same set).

`pre-auto-gc` is the one hook where a non-zero exit is not a failure: it tells
git not to bother with the collection, and the next command after the gate
finishes collects as usual. The marker it reads is ignored once it is older than
30 minutes, so a gate killed mid-run cannot wedge garbage collection forever.

Ruff is scoped to staged files on purpose: the repo carries 732 pre-existing
ruff errors, so a whole-tree lint would fail every commit and teach people to
bypass the hook. Pre-commit does the same by passing only changed filenames.

### pre-push stages

1. **Gate 1** — `scripts/pre_push_score.py` scores the commits being pushed and
   prints the band with the top SHAP reasons. Advisory; `GATE1_BLOCK=1` makes a
   high band block.
2. **ruff** over the outgoing diff only.
3. **pytest**. Skip with `GATEKEEPER_HOOK_TESTS=0` for WIP branches.

The pushed refs arrive on stdin in git's pre-push format; the hook reads stdin
exactly once and forwards it verbatim to the Gate 1 script.

## Commands

```bash
npm run hooks:init       # install the hooks and verify the wiring
npm run hooks:install    # install only
npm run hooks:uninstall  # unset core.hooksPath and remove .husky/_
npm run hooks:verify     # the doctor: assert the wiring invariants
npm run hooks:list       # print the hook inventory
```

The doctor takes three flags, which is why `hooks:list` exists as a shorthand:

```bash
npm run hooks:verify -- --strict   # promote "not installed here" warnings to failures
npm run hooks:verify -- --list     # the hook inventory, with kinds and modules
npm run hooks:verify -- --events   # the last 10 recorded hook events
```

`--strict` is what CI uses: the runner has just installed everything, so a
"missing from this machine" warning there really is a failure.

`hooks:verify` is worth running after any git config change — see
Troubleshooting.

## Tracing a hook

`HUSKY=2` is husky's own debug switch. It turns on `set -x` for the sh
dispatcher, and this repo continues the same trace into Python, where the
decisions actually happen:

```bash
HUSKY=2 git commit -m "feat: ..."
```

```
++ s=.husky/pre-commit
+ pre-commit: repo=/path/to/gatekeeper
+ pre-commit: interpreter=/path/to/venv/bin/python
+ pre-commit: argv=[]
+ pre-commit: linting 2 staged Python file(s)
+ git diff --cached --name-only --diff-filter=ACMR -- *.py (in /path/to/gatekeeper)
```

The interpreter line is the useful one: `bootstrap.sh` picks it before Python
starts, so it is otherwise invisible, and "which Python did the hook get?" is
the first question when a hook behaves differently in two terminals.

`GATEKEEPER_TRACE=1` does the same thing when husky is bypassed entirely — when
running a module directly, for instance in a test.

## Protected branches

`pre-merge-commit`, `pre-rebase` and `prepare-commit-msg` read
`protected_branches` from `.gatekeeper.yml`:

```yaml
protected_branches:
  - main
  - master
  - release/*
  - hotfix/*
```

Globs are supported. Without a `.gatekeeper.yml`, the list above is the
built-in default. `GATEKEEPER_ALLOW_PROTECTED=1` is the deliberate override:

```bash
GATEKEEPER_ALLOW_PROTECTED=1 git merge ...
```

## Bypassing

| Goal | Command |
|------|---------|
| Skip one hook | `GATEKEEPER_SKIP_HOOKS=pre-push git push` |
| Skip several | `GATEKEEPER_SKIP_HOOKS=commit-msg,pre-push git commit ...` |
| Skip everything (ours) | `GATEKEEPER_SKIP_HOOKS=all git commit ...` |
| Skip everything (husky) | `HUSKY=0 git commit ...` |
| Skip only the test stage | `GATEKEEPER_HOOK_TESTS=0 git push` |
| Allow a protected-branch operation | `GATEKEEPER_ALLOW_PROTECTED=1 git merge ...` |
| Force a specific Python | `GATEKEEPER_PYTHON=/path/to/python git push` |
| Skip hooks entirely (git) | `git commit -n` |

`GATEKEEPER_SKIP_HOOKS` is a comma list and only disables the hooks it names —
`commit-msg,pre-push` does not disable `pre-commit`.

## Startup files and CI

Husky sources `${XDG_CONFIG_HOME:-$HOME/.config}/husky/init.sh` before every
hook. That is the place for a Node version manager's setup, or to disable hooks
on a machine you do not want them on:

```sh
# ~/.config/husky/init.sh
export HUSKY=0
```

On CI, `install.mjs` skips installing by default because `CI=true`. Set
`HUSKY=1` to force a real install — that is how the hooks workflow exercises
the setup path instead of trusting it.

## Relationship to `.pre-commit-config.yaml`

`.pre-commit-config.yaml` is kept as the declarative record of the hook *policy*
(detect-secrets, ruff, the data-leakage check, Gate 1 scoring, pytest) and for
environments where the Python `pre-commit` tool is the installer. It is not
installed here, because installing it would fight husky for
`.git/hooks/pre-push` — the exact conflict this change removes.

If you want the pre-commit framework on a machine where husky is absent, run
`pre-commit install --hook-type pre-push` there; do not do both in one clone.

`gatekeeper init` detects this: if `.husky/` exists or `core.hooksPath` is set,
it leaves `.git/hooks` alone and points at `.husky/pre-push` instead of writing
a hook that would never run.

## Non-shell hooks

A hook does not have to be shell. `.husky/pre-commit` can call a sibling, which
husky documents and the doctor permits:

```shell
# .husky/pre-commit
node .husky/pre-commit.js
```

The doctor only complains about a file like `pre-commit.js` when the real
`.husky/pre-commit` is missing, since then nothing would ever run it.

## Troubleshooting

**Hooks stopped running entirely, with no error.**
Check `git config core.hooksPath`. It must be exactly `.husky/_`.

Husky's CLI treats *any* argument as the hooks directory, so
`npx husky --version` silently rewrites it to `--version/_` and creates a stray
`--version/` directory. This is a real footgun — it happened while building this
integration.

```bash
npm run hooks:verify                    # reports the mismatch
git config core.hooksPath .husky/_      # fix
rm -rf -- --version                     # clean up the stray directory
```

**A hook file exists but never runs.**
Run `npm run hooks:verify`. The two shapes that look right and are inert are
`precommit`/`pre_commit` (no dashes) and `pre-commit.sh` (an extension, with no
real `pre-commit` beside it). Upstream lists this as the first cause of "hooks
not running".

**"Python was not found; run without arguments to install from the Microsoft
Store".**
On Windows `command -v python3` matches the Store alias stub, which exists and
exits non-zero. `bootstrap.sh` probes each candidate with a real `python -c`
before trusting it. If nothing passes, set `GATEKEEPER_PYTHON`.

**A hook is unexpectedly slow.**
`pre-push` runs the test suite. `GATEKEEPER_HOOK_TESTS=0 git push` skips it.

**Husky says a hook "script failed (code N)".**
The shim ran but the delegated module failed. Run the module directly for the
full output, e.g. `python -m scripts.hooks.pre_push`.
