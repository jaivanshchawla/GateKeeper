# Git hooks with husky

This repo runs its git hooks through [husky](https://github.com/typicode/husky) 9.
Husky is only the *installer*: it owns `core.hooksPath` and keeps three
two-line shims in `.husky/`. Every rule lives in `scripts/hooks/`, in Python,
next to the rest of the project.

## Why husky at all

Before this, hook installation was split across two mechanisms that could not
both work:

| Mechanism | What it wrote | Problem |
|-----------|---------------|---------|
| `.pre-commit-config.yaml` + `pre-commit install --hook-type pre-push` | `.git/hooks/pre-push` | Untracked, so a fresh clone had no hook until someone ran the install command |
| `gatekeeper init` (the CLI) | `.git/hooks/pre-push` | Overwrote the file above, and baked in an absolute Windows path |

Git executes exactly one file per hook, so these silently clobbered each other.
Nothing tracked in the repo guaranteed a hook was installed at all.

Husky replaces that with one tracked, declarative installer: `npm install`
runs `prepare` → `husky` → `core.hooksPath` is set and the shims are live.

## Layout

```
package.json            husky devDependency + the scripts below
.husky/
  pre-commit            2-line shim
  commit-msg            2-line shim
  pre-push              2-line shim
  lib/bootstrap.sh      finds a working Python 3 to start a hook
  _/                    generated by husky on `npm install` (gitignored)
scripts/hooks/
  _runtime.py           repo root, interpreter resolution, git helpers
  commit_msg.py         conventional-commit rules
  pre_commit.py         staged-file lint + conflict markers
  pre_push.py           Gate 1 + diff-scoped ruff + pytest
  verify.py             wiring doctor
tests/test_hooks.py     unit tests for all of the above
```

Two rules keep this readable:

1. **`.husky/<hook>` files contain no logic.** Two lines — source the
   bootstrap, delegate to a script. Anything longer belongs in `scripts/hooks/`
   where it can be unit-tested.
2. **Interpreter resolution happens in one place.** `bootstrap.sh` only decides
   which Python can *start* a hook; `_runtime.py` decides which Python runs the
   project's tooling. They are separate problems and live in separate files.

## The hooks

### `pre-commit` — blocks

- `ruff check` over the **staged Python files only**.
- Leftover merge-conflict markers in the staged content, read from git's own
  `diff --cached --check`.

Ruff is scoped to staged files for a reason: the repo currently reports 732
pre-existing ruff errors, so a whole-tree lint here would fail every commit and
teach people to bypass the hook. Same reasoning as pre-commit's own
changed-files behaviour.

### `commit-msg` — blocks

Enforces `type(scope): subject`. The type allow-list is read off this repo's
own history instead of being invented:

```
feat fix docs style refactor perf test build ci chore revert
meas eval analysis backfill
```

Merge, revert, `fixup!`, `squash!` and `WIP` subjects pass through untouched.
Subjects are capped at 100 characters and may not end in a period.

### `pre-push` — Gate 1 warns, ruff and pytest block

1. **Gate 1** — `scripts/pre_push_score.py` scores the commits being pushed and
   prints the band with the top risk reasons. Advisory by default; set
   `GATE1_BLOCK=1` to make a high band block the push. This is the project's
   own product surface, so the hook calls it rather than reimplementing it.
2. **ruff** over the outgoing diff only.
3. **pytest** over `tests/`.

The pushed refs arrive on stdin in git's pre-push format. The hook reads stdin
exactly once and forwards it verbatim to the Gate 1 script.

## Installing

```bash
npm install          # runs `husky` via the prepare script
npm run hooks:verify # confirm the wiring
```

`npm run hooks:verify` is worth running after any git config change; see
Troubleshooting.

## Bypassing

| Goal | Command |
|------|---------|
| Skip one hook | `GATEKEEPER_SKIP_HOOKS=pre-push git push` |
| Skip several | `GATEKEEPER_SKIP_HOOKS=commit-msg,pre-push git commit ...` |
| Skip everything | `GATEKEEPER_SKIP_HOOKS=all git commit ...` |
| Skip via husky | `HUSKY=0 git commit ...` |
| Skip only the test stage | `GATEKEEPER_HOOK_TESTS=0 git push` |
| Force a specific Python | `GATEKEEPER_PYTHON=/path/to/python git push` |

`GATEKEEPER_SKIP_HOOKS` is a comma list and only disables the hooks it names —
`commit-msg,pre-push` does not disable `pre-commit`.

## Relationship to `.pre-commit-config.yaml`

`.pre-commit-config.yaml` is kept as the declarative record of the hook *policy*
(detect-secrets, ruff, the data-leakage check, Gate 1 scoring, pytest) and as
the path used in environments where the Python `pre-commit` tool is the
installer. It is not installed here, because installing it would fight husky
for `.git/hooks/pre-push` — the exact conflict this change removes.

If you want the pre-commit framework on a machine where husky is absent, run
`pre-commit install --hook-type pre-push` there; do not do both in one clone.

`gatekeeper init` now detects this: if `.husky/` exists or `core.hooksPath` is
set, it leaves `.git/hooks` alone and points at `.husky/pre-push` instead of
writing a hook that would never run.

## Troubleshooting

**Hooks stopped running entirely, with no error.**
Check `git config core.hooksPath`. It must be exactly `.husky/_`.

Husky's CLI treats *any* argument as the hooks directory, so
`npx husky --version` (a natural thing to type) silently rewrites it to
`--version/_` and creates a stray `--version/` directory. This is a real
footgun, not a hypothetical — it happened while building this integration.

```bash
npm run hooks:verify                    # reports the mismatch
git config core.hooksPath .husky/_      # fix
rm -rf -- --version                     # clean up the stray directory
```

**"Python was not found; run without arguments to install from the Microsoft
Store".**
On Windows, `command -v python3` matches the Store "App execution alias" stub,
which exists and exits non-zero. `.husky/lib/bootstrap.sh` probes each candidate
with a real `python -c` before trusting it, so this no longer breaks the hooks.
If you still hit it, set `GATEKEEPER_PYTHON`.

**Husky says a hook "script failed (code N)".**
The shim ran but the delegated script failed. Run the script directly for the
full output, e.g. `python scripts/hooks/pre_push.py`.
